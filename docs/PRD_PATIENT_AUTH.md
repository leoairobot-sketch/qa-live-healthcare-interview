## 1. 产品概述

### 1.1 背景

当前问诊用户进入问诊流程使用「姓名 + 生日」在前端本地比对 `patient-user.json` 的方式验证身份：无真实账号体系、验证逻辑在浏览器端可绕过、无会话保持，也无法为后续问诊记录提供可信归属。需要为问诊用户提供基于用户名密码的注册与登录能力，由后端（qa-service-user）统一管理账号与会话。

### 1.2 目标

为问诊用户建立后端账号体系：注册、登录、登出、会话保持；发起问诊必须先登录，登录用户的姓名自动带入问诊流程。可量化指标：登录/注册接口本地环境 P95 响应时间 < 500ms，P0 验收场景通过率 100%。

### 1.3 范围（In Scope）

- 问诊用户注册（用户名 + 密码 + 姓名），密码 bcrypt 加密存储于 MySQL
- 问诊用户登录 / 登出（服务端内存 Session，JSESSIONID Cookie）
- 会话身份查询接口（`GET /api/auth/me`），供前端刷新后恢复登录态
- 前端登录页 / 注册页、导航栏「问诊用户登录」入口与已登录态展示
- 问诊门禁：未登录访问问诊相关页面重定向登录页，登录成功后回跳
- 游客可自由浏览首页、医生列表、关于页（无需登录）
- 移除旧的「姓名 + 生日」验证入口，问诊用户姓名由登录态自动带出

### 1.4 非目标（Out of Scope）

- 不做找回密码、修改密码、记住我、第三方 OAuth 登录（本期无通知渠道与需求，降低范围）
- 不做 JWT/Token 方案（经确认采用 Session；升级 JWT 留待后续）
- 不做 Session 持久化（内存 Session，后端重启后需重新登录；单实例部署场景可接受）
- 不改造医生登录（医生仍走现有前端 JSON 校验，属既有范围约定）
- 不迁移存量 `patient-user.json` / `question-list.json` 历史数据（旧数据仅前端展示用，无账号映射关系）
- 不做多端会话管理与踢下线

### 1.5 名词解释

| 术语 | 定义 |
|---|---|
| 问诊用户 | 注册并登录后可向医生发起问诊的普通用户（患者） |
| 游客 | 未注册/未登录的访问者，仅可浏览公开页面 |
| Session | 服务端内存保存的会话状态，通过响应下发的 JSESSIONID Cookie 关联 |
| bcrypt | 自适应密码哈希算法，本功能用于密码存储（强度因子 10） |
| 问诊门禁 | 前端路由守卫：未登录访问问诊相关页面时重定向到登录页 |

## 3. 用户故事

- US-1（P0）：作为问诊用户，我想要用用户名和密码注册账号，以便拥有专属的问诊身份。
- US-2（P0）：作为问诊用户，我想要用用户名密码登录与登出，以便安全地使用问诊功能。
- US-3（P0）：作为问诊用户，登录后发起问诊时系统自动带出我的姓名，以便不必重复填写身份信息。
- US-4（P0）：作为问诊用户，我希望未登录时无法进入问诊页并被引导去登录，登录后回到我要去的页面，以便流程不中断。
- US-5（P1）：作为问诊用户，我希望登录后刷新页面仍保持登录态，以便中途不被强迫重新登录。
- US-6（P1）：作为游客，我想先自由浏览首页和医生列表，以便降低注册门槛。

## 4. 功能需求

### 4.1 功能清单

| 编号 | 功能点 | 优先级 | 说明 |
|---|---|---|---|
| F-1 | 用户注册 | P0 | 用户名+密码+姓名创建账号，密码 bcrypt 入库，成功后自动登录 |
| F-2 | 用户登录 | P0 | 校验凭据，建立服务端 Session，下发 JSESSIONID Cookie |
| F-3 | 用户登出 | P0 | 销毁 Session 与 Cookie，导航栏恢复游客态 |
| F-4 | 会话保持与登录态恢复 | P0 | 刷新页面经 /api/auth/me 恢复登录态；Session 30 分钟不活动过期 |
| F-5 | 问诊门禁与旧流程替换 | P0 | 未登录访问问诊页重定向登录页并支持回跳；移除姓名+生日表单 |
| F-6 | 游客浏览不受限 | P1 | 首页/医生列表/关于页对游客开放 |

### 4.2 功能详细描述

#### F-1 用户注册

- 入口：登录页（`/login`）内「注册」切换项；导航栏「问诊用户登录」按钮进入登录页后可达
- 流程：填写用户名（3–32 位，字母/数字/下划线）、密码（≥6 位）、姓名（2–32 位）→ 前端校验 → `POST /api/auth/register` → 成功后服务端直接建立会话（自动登录）→ 跳转首页或 redirect 目标页
- 异常场景：
  - 用户名已存在：提示「用户名已被占用」，聚焦用户名输入框
  - 字段不合法（长度/字符集）：字段下方行内提示具体规则
  - 后端不可用：页面顶部提示「服务暂不可用，请稍后重试」，保留已填内容

#### F-2 用户登录

- 入口：导航栏「问诊用户登录」按钮 → `/login`
- 流程：输入用户名+密码 → `POST /api/auth/login` → 成功建立 Session、前端记录用户信息并跳转 redirect 目标页或首页 → 导航栏显示「你好，<姓名>」与「退出登录」
- 异常场景：
  - 凭据错误（用户不存在或密码错误）：统一提示「用户名或密码错误」，不区分具体原因（防止用户名枚举）
  - 后端不可用：提示「服务暂不可用，请稍后重试」

#### F-3 用户登出

- 入口：导航栏已登录用户名下拉菜单中的「退出登录」
- 流程：`POST /api/auth/logout`（携带 Cookie）→ 服务端销毁 Session → 前端清空本地用户态 → 返回首页，导航栏恢复「问诊用户登录」按钮

#### F-4 会话保持与登录态恢复

- Cookie 属性：HttpOnly、SameSite=Lax、路径 `/`；开发环境经 Vite 代理同源访问，无跨域 Cookie 问题
- 过期策略：服务端 Session 30 分钟不活动过期；过期后访问受保护资源返回 401，前端清除本地态并引导重新登录
- 恢复策略：前端应用启动 / 刷新时调用 `GET /api/auth/me`，200 则恢复导航栏登录态，401 则保持游客态（静默处理，不弹提示）

#### F-5 问诊门禁与旧流程替换

- 门禁：路由守卫拦截 `/consultation/*`：未登录 → 重定向 `/login?redirect=<原路径>`；登录/注册成功后优先跳转 redirect 参数指定的页面
- 替换：移除问诊页「姓名 + 生日」验证表单与 `verifyPatient` 调用；问诊提交中的患者身份（patientId/patientName）取自当前登录会话
- 边界：医生登录入口与医生工作台不受门禁影响（`/doctor-login`、`/doctor-room/*` 不在拦截范围）

#### F-6 游客浏览不受限

- 首页 `/`、医生列表 `/doctors`、关于页 `/about` 无需登录
- 游客在医生列表点「进入诊室」：因目标 `/consultation/*` 受门禁保护，自动转入登录引导，登录成功后回到该医生问诊页

## 5. 接口设计

服务：qa-service-user（8080），沿用现有 REST 风格与 CORS 配置；除登录态接口外均为 JSON 请求/响应。

### 5.1 接口清单

| 编号 | 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|---|
| API-1 | POST | /api/auth/register | 注册并自动登录 | 否 |
| API-2 | POST | /api/auth/login | 登录，建立 Session | 否 |
| API-3 | POST | /api/auth/logout | 登出，销毁 Session | 是（需会话） |
| API-4 | GET | /api/auth/me | 查询当前会话用户 | 是（需会话） |
| API-5 | GET | /api/doctors | 医生列表（需求2 已交付，游客可访问） | 否 |

### 5.2 接口详情

#### API-1 POST /api/auth/register

请求体：

| 字段 | 类型 | 必填 | 校验规则 |
|---|---|---|---|
| username | string | 是 | 3–32 位，仅字母/数字/下划线，全局唯一 |
| password | string | 是 | ≥6 位，≤64 位 |
| name | string | 是 | 2–32 位中文或字母 |

成功响应 `201`：
```json
{ "id": 1, "username": "patient001", "name": "张三" }
```
（同时下发 Set-Cookie: JSESSIONID=...，注册即登录）

错误码：

| 状态码 | 场景 | 响应示例 |
|---|---|---|
| 400 | 字段校验失败 | `{ "message": "密码长度不能少于6位" }` |
| 409 | 用户名已存在 | `{ "message": "用户名已被占用" }` |

#### API-2 POST /api/auth/login

请求体：`{ "username": string, "password": string }`（均必填）

成功响应 `200`：
```json
{ "id": 1, "username": "patient001", "name": "张三" }
```
Set-Cookie: `JSESSIONID=...; HttpOnly; SameSite=Lax`

错误码：

| 状态码 | 场景 | 响应示例 |
|---|---|---|
| 401 | 用户不存在或密码错误（统一文案） | `{ "message": "用户名或密码错误" }` |

#### API-3 POST /api/auth/logout

- 请求：无请求体，携带 JSESSIONID Cookie
- 成功响应 `200`：`{ "message": "已退出登录" }`，服务端 Session 失效
- 无有效会话时也返回 200（幂等）

#### API-4 GET /api/auth/me

- 请求：携带 JSESSIONID Cookie
- 成功响应 `200`：`{ "id": 1, "username": "patient001", "name": "张三" }`
- 未登录/会话过期响应 `401`：`{ "message": "未登录或会话已过期" }`

## 6. 数据模型

### 6.1 核心实体

问诊用户（patient_user）与问诊记录（question，现有前端本地数据）为 1—N 关系；本期仅落地 patient_user 表，问诊记录仍存前端（非目标）。

### 6.2 数据表结构

表：`qa_live.patient_user`（Flyway V2 迁移脚本创建，沿用 V1 版本化管理模式）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 用户 ID |
| username | VARCHAR(32) | NOT NULL, UNIQUE | 登录用户名（唯一索引 uk_patient_username） |
| password_hash | VARCHAR(100) | NOT NULL | bcrypt 哈希（强度 10），禁止存明文 |
| name | VARCHAR(32) | NOT NULL | 患者姓名，问诊展示用 |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 注册时间 |

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 密码 bcrypt（强度 10）存储，任何接口/日志不得出现明文密码；登录失败统一文案防用户名枚举；JSESSIONID Cookie 置 HttpOnly + SameSite=Lax；Session 服务端内存保存，30 分钟不活动过期 |
| 性能 | 注册/登录接口本地环境 P95 < 500ms（含 bcrypt 计算约 50–100ms） |
| 兼容性 | Chrome / Safari 最近两个大版本；1440px 及以上分辨率与移动端 375px 布局可用 |
| 可维护性 | 沿用 qa-service-user 现有分层（controller/service/repository）；数据库变更一律走 Flyway 版本化迁移；前端沿用 Vue3 组合式 API 与 ant-design-vue 组件 |

## 8. 验收标准（可测试）

### 8.1 用户注册

#### Requirement: 系统应当提供问诊用户注册能力
系统**应当(SHALL)**接受合法的用户名、密码、姓名创建问诊用户账号，密码以 bcrypt 哈希存储，注册成功即建立会话。

- **Scenario: 合法输入注册成功**
  - **WHEN** 以 `{"username":"patient001","password":"123456","name":"张三"}` 调用 POST /api/auth/register
  - **THEN** 返回 201 与 `{id, username, name}`，Set-Cookie 下发 JSESSIONID；数据库 patient_user 表新增一行，password_hash 以 `$2a$` 开头（bcrypt）
- **Scenario: 用户名已存在**
  - **WHEN** 使用已注册的用户名再次调用注册接口
  - **THEN** 返回 409，message 为「用户名已被占用」，数据库不新增记录
- **Scenario: 字段不合法**
  - **WHEN** 提交密码长度 5 位（或姓名 1 位）的注册请求
  - **THEN** 返回 400，message 说明具体校验规则

### 8.2 用户登录

#### Requirement: 系统应当校验用户名密码并建立会话
系统**应当(SHALL)**对已注册用户提供用户名密码登录：成功建立服务端 Session 并返回用户信息，失败返回 401。

- **Scenario: 正确的用户名和密码**
  - **WHEN** 用户以正确用户名和密码调用 POST /api/auth/login
  - **THEN** 返回 200、`{id, username, name}` 与有效 JSESSIONID Cookie
- **Scenario: 密码错误**
  - **WHEN** 用户以错误密码调用登录接口
  - **THEN** 返回 401，提示「用户名或密码错误」，且不区分是用户名还是密码错误
- **Scenario: 用户不存在**
  - **WHEN** 以未注册的用户名调用登录接口
  - **THEN** 返回 401，提示文案与密码错误场景完全一致

### 8.3 会话保持与身份查询

#### Requirement: 系统应当通过会话识别已登录用户
系统**应当(SHALL)**依据 JSESSIONID 会话识别用户：GET /api/auth/me 对有效会话返回当前用户，对无会话/过期会话返回 401。

- **Scenario: 携带登录 Cookie 查询身份**
  - **WHEN** 登录成功后携带 JSESSIONID 调用 GET /api/auth/me
  - **THEN** 返回 200 与当前用户 `{id, username, name}`
- **Scenario: 无 Cookie 或会话过期**
  - **WHEN** 不带 Cookie（或 Session 已过期）调用 GET /api/auth/me
  - **THEN** 返回 401
- **Scenario: 登出后会话失效**
  - **WHEN** 调用 POST /api/auth/logout 后再以原 Cookie 调用 GET /api/auth/me
  - **THEN** 返回 401

### 8.4 用户登出

#### Requirement: 系统应当提供登出能力并使会话失效
系统**应当(SHALL)**在登出时销毁服务端 Session，登出接口对无会话调用幂等返回 200。

- **Scenario: 登录后登出**
  - **WHEN** 登录后携带 Cookie 调用 POST /api/auth/logout
  - **THEN** 返回 200，原 Session 失效（由 8.3 场景验证）

### 8.5 问诊门禁（前端）

#### Requirement: 未登录访问问诊页面应当重定向登录页并支持回跳
前端**应当(SHALL)**对 `/consultation/*` 路由实施登录校验：未登录重定向到 `/login?redirect=<原路径>`，登录/注册成功后跳转 redirect 目标。

- **Scenario: 游客直接访问问诊页**
  - **WHEN** 未登录状态浏览器打开 `/consultation/dr-zhang-wei`
  - **THEN** 重定向到 `/login?redirect=/consultation/dr-zhang-wei`
- **Scenario: 登录后回到目标页**
  - **WHEN** 在上述登录页完成登录
  - **THEN** 自动跳转回 `/consultation/dr-zhang-wei`，页面正常，问诊提交人姓名为登录用户姓名

### 8.6 游客浏览（前端）

#### Requirement: 游客应当可以浏览公开页面
系统**应当(SHALL)**允许未登录用户浏览首页、医生列表与关于页。

- **Scenario: 游客浏览医生列表**
  - **WHEN** 未登录状态访问 `/`、`/doctors`、`/about`
  - **THEN** 页面正常渲染，不发生登录重定向

### 8.7 旧流程下线（前端）

#### Requirement: 姓名生日验证入口应当移除
系统**应当(SHALL)**移除问诊流程中「姓名 + 生日」验证表单，问诊患者身份改由登录会话提供。

- **Scenario: 问诊页不再出现旧表单**
  - **WHEN** 已登录用户进入问诊页
  - **THEN** 页面无姓名/生日输入项，提交的问题归属当前登录用户（patientName 为登录姓名）

## 9. 任务拆分与里程碑

| 步骤 | 子任务 | 交付物 | 依赖 | 验收方式 |
|---|---|---|---|---|
| T-1 | patient_user 表 Flyway V2 迁移 | `V2__init_patient_user.sql` | 无 | 服务启动后 phpMyAdmin 可见表结构与唯一索引 |
| T-2 | 后端 auth 接口（register/login/logout/me）+ bcrypt + Session | 可运行的服务代码 | T-1 | curl 逐条通过第 8.1–8.4 全部 Scenario |

## 11. 风险与依赖

| 风险/依赖 | 影响 | 应对 |
|---|---|---|
| 内存 Session 后端重启后丢失登录态 | 低 | 用户重新登录即可；PRD 已列为非目标，后续可升级 Spring Session JDBC 持久化 |
| bcrypt 计算（强度 10）增加注册/登录耗时 | 低 | 单次约 50–100ms，远低于 500ms 指标；不盲目调高强度 |
| 注册接口 409 可被用于探测用户名是否已注册 | 低 | 属可接受的常规取舍（注册场景无法完全隐藏）；登录接口已做统一文案防枚举 |
| 前后端 Cookie 跨域问题 | 低 | 开发环境前端经 Vite 代理同源访问后端，SameSite=Lax 不受影响 |
| 依赖需求2 已交付的 MySQL/Flyway 基础设施 | 中 | T-1 直接复用 V1 模式；如 MySQL 未启动，后端无法完成迁移（启动顺序：compose → 后端 → 前端） |
